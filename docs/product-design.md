# 현재 제품 설계

## 승인된 흐름

사용자가 2026-10-01 승인한 흐름이다. 아래 접속·검사 명세는 분석을 반영한 구현 설계안이다. 사용자 확정 정책과 구분하며, 실제 지원·정확성·성능이 검증됐다는 뜻은 아니다. 제품 경계는 [RULE](../RULE.md), 검사 근거는 [연구 연결](research-to-product.md), 구현 확인 조건은 [요구사항](requirements.md)을 따른다.

1. 첫 화면: 논문 제목·도움 문장, 새 검사·결과 열기·작동 방식 보기.
2. 연결: 원본·대상 접속 정보를 입력하고 DBMS·버전·접속·조회 가능 범위를 사전 확인한다.
3. 선택: 데이터, 구조·제약, 사용자·권한, 관련 객체, 별도 공간의 동작 시험. 가능·일부 가능·추가 준비 필요·확인 불가를 안내한다. 자동 대응을 확인하고 이름 변경을 연결한다.
4. 실행 전: 접속 대상·검사 목록·변경 여부·제외 및 확인 불가 영역을 요약한다. 쓰기는 시험 DB에만 수행한다.
5. 실행: 세부 검사 진행, 취소, 연결 끊김·시간 초과 등 방해를 표시한다. 완료·중단·미시작을 구분한다.
6. 결과: 대분류별 판정과 건수, 펼칠 수 있는 세부 검사·안전한 위치·차이 종류·판정 근거. 실제 값은 표시하지 않는다.
7. 저장: 검사 범위·결과·미검증 이유를 로컬에 저장하고 다시 열거나 CSV·HTML로 내보낸다.

## 웹 시안의 실제 앱 이식 기준

2026-10-02 후속 사용자 확정으로 복제 작업은 [MASTER_RULES](replica/MASTER_RULES.md), [컴포넌트 지도](replica/COMPONENT_TREE.md), [현재 상태](replica/COMPONENT_STATUS.md), `replica/specs/`를 따른다. 아래 제품 흐름·과거 교정안으로 실행 원본을 재해석하지 않는다. 원본 화면과 실제 DB 지원/OS 기능의 대응 차이는 해당 명세에 기록하고 임의 완료 면제하지 않는다. UI-ALIGN-01은 당시 페이지 교정 이력이며 새 복제 작업의 LOCK 증거가 아니다.

## 화면별 버튼 설계와 완료 점검

사용자 확정 기준은 [RULE의 UI-01–UI-04](../RULE.md), 다음 화면 작업의 디자인 맥락은 [brief](../.ui-craft/brief.md)를 읽는다. 화면을 그릴 때 아래 목록을 먼저 작성하고 구현·수정 후 같은 목록으로 점검한다. 기능만 연결되거나 hover만 있는 버튼을 완료로 처리하지 않는다.

| 버튼 ID·이름 | 중요도와 근거 | 크기·배치·강조 | 실행 기능·다음 상태 | 포인터·초점·누름·비활성 피드백 | 처리 중·성공·실패 피드백 | 실행 애니메이션·동작 줄이기 대응 | 실제 확인 증거 |
|---|---|---|---|---|---|---|---|

이 표는 작성 형식이며 실제 화면의 버튼을 설계/구현했다고 뜻하지 않는다. 각 화면의 주요 행동을 먼저 정한 뒤 보조·취소/중단을 배치한다. 화면 전환 후 초점·현재 단계·다음 행동도 함께 확인한다. 상태는 버튼 기능에 해당하는 것을 명시하고 해당하지 않는 상태는 이유를 적는다.

실행 애니메이션은 클릭 접수와 실제 작업의 상태 변화에 연결한다. 연결·검사·저장은 시작/처리/성공/실패를 구분하고, 펼침·닫기·다음 단계는 공간/상태 전환을 드러낸다. 성공 표현은 실제 성공 시점에만 한다. 처리 중 중복 실행 방지와 취소 가능 여부를 명시한다. 전체 화면의 과도한 움직임이나 반복 장식으로 필수 동작 피드백을 대신하지 않는다.

화면 완료 판단에는 [DMV-12.1–DMV-12.4](requirements.md)의 실제 증거를 연결한다. 버튼 목록의 빈 항목·누락된 상태/애니메이션·미확인 동작이 남으면 완료가 아니라 설계 중/구현 중/검증 대기로 표시한다.

## 화면 시안의 구성 — 2026-10-01 초안

[화면 토큰](../.ui-craft/tokens.md)은 PlandoSee 제약 해제 뒤 사용자의 Discord 테마 제안을 반영한 다크 시안의 설계안이다. 화면 시안은 [예시 HTML](../examples/ui-prototype/index.html)에서 흐름과 애니메이션을 검토한다. 화면에 항상 예시임을 표시한다. 실제 DB 접속·검사·OS 보안 저장소·앱 배포는 수행하지 않는다. 실제 판정 모델은 아래 기술 설계를 따른다.

### 첫 화면의 문장과 세 행동

- **논문 제목:** Functional Success versus Database-State, Behavioral, and Operational Contracts in AI-Generated PostgreSQL Schema Migrations.
- **도움 문장:** 마이그레이션을 마친 개발자가 논문의 다축 검증 방법으로 두 DB의 데이터·구조·권한·객체를 비교하고, 차이와 확인하지 못한 영역을 찾도록 돕습니다.
- **사용자 행동 세 가지:** ① 원본·대상에 연결하고 조회 범위를 확인한다. ② 검사 분류·테이블 대응을 선택해 비교를 실행한다. ③ 차이·미검증 이유를 확인하고 결과를 저장한다.
- **연구 설명 P1:** 기본 기능 성공과 넓은 DB 계약 충족은 구분해야 한다는 연구 관찰을 분류별 검사와 미검증 표시로 반영한다. 데이터 손상률·산업 오류율·제품 탐지 성능으로 논문 수치를 표현하지 않는다.

### 공통 골격과 정보 우선순위

```text
데스크톱
┌──────────────────────────────────────────────────────────────┐
│ 앱 이름                    현재 검사 / 예시 표시       언어   │
├───────────────┬──────────────────────────────────────────────┤
│ 새 검사       │ 현재 단계 제목 + 지금 할 일                   │
│ 1 연결        │                                              │
│ 2 사전 확인   │ 주요 폼 / 범위 / 진행 / 결과                  │
│ 3 검사 선택   │                                              │
│ 4 실행 전     │ 세부 정보는 필요한 행에서 펼침                │
│ 5 진행        │                                              │
│ 6 결과        ├──────────────────────────────────────────────┤
│ 7 저장        │ 뒤로 / 범위 안내                [핵심 행동]   │
└───────────────┴──────────────────────────────────────────────┘

작은 데스크톱 창도 동일한 왼쪽 단계 목록·본문·고정 하단 구조를 유지한다.
폼과 결과는 본문 안에서 스크롤하며 모바일 가로 단계 목록으로 전환하지 않는다.
```

P0는 제목·현재 단계·주요 입력/결과·제한 범위·다음 행동이다. P1은 TLS/권한 준비·세부 검사·대응 편집·연구 근거·원본 결함/정리 내역이다. P2는 자원 설정·보안 저장소 선택·버전 정보다. 관련 문제 발생 시 그 P1/P2 정보를 P0 안내로 올린다. 목록과 표는 고정 행동 영역에 가리지 않게 본문만 스크롤한다.

**플랫폼 기준:** Windows/macOS 데스크톱 전용이다. 초기 창 최소 크기는 960×720 DIP 설계안이며 Avalonia 구현에서 `MinWidth`·`MinHeight`와 실제 OS 배율을 확인한다. HTML은 이 구조의 검토용 시안이다. 모바일용 breakpoint·모바일 화면·모바일 테스트를 넣지 않는다. 브라우저에서 창 크기를 확인한 결과를 실제 Avalonia·OS 배율 검증으로 기록하지 않는다.

### 상태 범위

미시작·처리 중·빈 목록·오류·일부 조회·확인 불가·중단·완료·저장 실패는 필수다. offline은 자동 대기/재개가 아니라 연결 실패 또는 검사 중단으로 처리한다. 공동 편집 충돌은 해당 없지만 테이블 대응 중복과 실행 전 설정 변경은 필수로 다룬다. 다음 단계가 불가능하면 버튼 옆에 이유와 수정 행동을 둔다. 입력은 뒤로 이동해도 유지하지만 수정 후 연결·범위 확인의 유효성을 다시 계산한다. 정상 진행 중 미래 단계로 건너뛰는 메뉴는 비활성이다.

### 버튼별 설계 목록

선택 요소는 네 DBMS 카드 → 원본/대상 입력 → 사전 확인 → 분류 선택 → 테이블 검색/선택 → 필요한 대응 변경 순으로 배치한다. 대응 drawer는 원본 이름, 검색 필드, 선택 가능한 대상 목록, 충돌 이유, 취소/적용을 한 화면에 둔다. 검색·목록은 상태를 설명하고 결과가 없으면 검색어를 바꿀 수 있다. 검색은 선택 범위를 바꾸지 않으며 일괄 선택은 현재 검색 결과에만 적용한다. 전체 선택 checkbox는 일부 선택 상태를 지원한다. 기존 민감 값 비노출·일대일 대응·이름 차이 보고를 유지한다.

### 통계 시각화와 LiveCharts2 구현 계획

실제 Avalonia 차트는 사용자의 LiveCharts2 제안을 유지한다. 전용 설치 스킬은 확인되지 않았으며 [공식 Avalonia 설치 안내](https://livecharts.dev/docs/avalonia/latest/overview.installation)의 `LiveChartsCore.SkiaSharpView.Avalonia`를 구현 단계에서 검토한다. 버전 고정과 두 OS의 실제 실행은 아직 검증하지 않았다.

**2026-10-01 화면 피드백 반영 설계:** 분석 질문은 “어느 분류에 불일치와 확인하지 못한 검사가 남았는가”다. 집계는 같은 `run.groups`를 사용한다. 누적 막대와 중복 요약 표를 합쳐, 분류별 전체 행 버튼 안에 세 판정의 정확한 숫자와 공통 축의 작은 막대를 둔다. 숫자·상태 이름을 기본 표시하고 행 클릭 또는 Enter/Space로 세부 검사·미검증 이유를 연다. 한 화면에 비교 행 최대 4개와 선택 시험 행 1개만 렌더링한다. 현재 HTML은 DOM/CSS만 사용하고 외부 라이브러리·새 네트워크 요청·URL 상태 저장을 추가하지 않는다. 결과 파일 다시 열기와 기존 필터 상태를 유지한다. 색·막대 없이도 열 이름과 숫자로 읽을 수 있다. 모바일은 사용자 확정 범위 밖이다.

- [Heer & Bostock (2010), Graphical Perception](https://hci.stanford.edu/publications/2010/crowd-perception/heer-chi2010.pdf): 수치 비교의 위치·길이 인지 실험을 참고했다. 이를 이 화면에 적용해 쌓인 구간을 해독하는 대신 각 판정을 0에서 시작하는 열로 분리하고, 모든 막대에 같은 건수 축을 쓴다. 정확한 숫자를 직접 표시한다. 이는 설계 적용이며 우리 화면의 사용자 성능 향상이 입증됐다는 주장은 아니다.
- [Heer & Robertson (2007), Animated Transitions](https://sites.stat.columbia.edu/gelman/communication/HeerRobertson2007.pdf): 상태 사이의 연결을 유지하는 전환과 의미를 왜곡하는 애니메이션의 위험을 참고했다. 새 결과 보기·파일 재열기 때 숫자를 220ms로 강조하고 막대는 320ms 이내에 정착시킨다. 실제 숫자는 첫 프레임부터 최종값이며 카운트업으로 가짜 중간 판정을 만들지 않는다. 필터·언어 변경·세부 창 닫기에는 차트 진입을 반복하지 않는다. 기능·상세 열기는 애니메이션을 기다리지 않는다. 동작 줄이기에서는 정적 최종 수치와 상태 문구가 유지된다.
- [LiveCharts2 공식 축 문서](https://livecharts.dev/docs/avalonia/latest/CartesianChart.Axes%20properties): 실제 앱에서도 0 기준선·공통 `MinLimit`/`MaxLimit`·정수 단위 축을 유지할 계획이다. 성능·상호작용은 실제 Avalonia 구현에서 확인한다.

비교 집계는 검사 항목 수다. 행 수나 전체 DB 성공률로 바꾸지 않는다. 중단·미시작·미확정 항목은 미검증으로 남긴다. 선택 제외·적용 대상 아님은 별도 범위로 표시한다. 별도 시험의 기대 충족/불충족·미검증, 정리 실패·남은 변경은 비교 차트에서 분리한다. HTML 차트는 LiveCharts2 실행이나 실제 DB 검증 증거가 아니다. 결과 합계·0값·중단·별도 시험·KR/EN·키보드·동작 줄이기·960 DIP 이상 창·파일 재열기를 시안에서 점검한다.

### 화면 피드백의 상시 적용 기준

- 안내 아이콘과 사전 확인 상태 표시·버튼은 상하 중앙 정렬한다. 상태 설명은 별도 안내 열에 둔다.
- 분류 헤더는 기본 약 64 DIP로 줄이고, 선택 체크박스의 44 DIP 조작 영역과 펼침 영역을 분리한다. 헤더의 체크박스 외 영역 전체가 펼침 버튼이며 두 행동은 서로 실행하지 않는다. 실제 버튼·체크박스 의미와 키보드 접근을 유지한다.
- 시험 준비 확인 후에는 준비 수정 버튼 우측에 DBMS·예시 서버·DB 이름을 표시한다. 준비 전 안내는 준비 완료 문구로 바뀐다. 준비 정보·DBMS·원본/대상 연결을 수정하거나 시험안 확인을 해제하면 완료 상태·표시가 무효화되고 재확인해야 한다. 비밀번호·시험 실제 값은 이 요약에 넣지 않는다.
- 결과 분류의 전체 행을 상세 버튼으로 만든다. 시작 화면은 새 검사·검사 결과 파일로 보기·예시 보기를 하나의 가로 행동 영역에 둔다. 두 주요 진입 버튼은 224w·52h로 정렬하고 새 검사는 채움, 파일 열기는 외곽선, 예시는 낮은 강조로 구분한다. 새 검사 문구는 버튼 중앙이며 화살표는 우측에 고정한다. 바로 아래에 연결·새 검사 없이 저장 JSON을 열 수 있다는 안내를 둔다. 지원하지 않는 파일·손상 파일은 안전하게 오류를 표시한다.

### 시안에서 남겨 둘 한계

UI 골격·문구·토큰·버튼 위계는 제안이며 사용자 검토 전 확정 승인을 기록하지 않는다. HTML은 데스크톱의 예시 상태를 재현하는 시안이다. 실제 드라이버 권한 탐지·정밀 값 비교·임시 보안·시험 쓰기·네이티브 파일 dialog·Keychain/Windows vault를 구현했다고 표시하지 않는다. 첫 방문 동료 평가와 두 OS의 Avalonia 입력/애니메이션·배율 검증은 실제 구현 단계에 남는다.

## 판정 모델

실행 상태(미시작·진행·완료·중단), 검증 판정(일치·불일치·판정 불가·미검증), 범위(선택·선택 안 함·적용 대상 아님)를 분리한다. 동작 시험은 기대 충족·기대 불충족으로 표현하고 정의 비교와 혼동하지 않는다.

선택 범위의 모든 필수 검사가 끝나야 '선택 범위 내 일치'라고 표시할 수 있다. 집계는 아래 결과 모델을 따른다. 원본 결함의 표시는 RULE.md를 따른다.

동작 시험 결과에는 시험 자체의 판정과 정리 결과를 별도로 표시한다. 정리 정책은 [RULE](../RULE.md)이 정본이며, 정리 실패와 남은 변경·확인 불가 영역을 시험 통과에 가려 숨기지 않는다.

## 구현 구성과 검증 목표 환경

공통 C# 비교 엔진을 Avalonia 화면에서 호출한다. 연결·catalog·자료형 처리는 DBMS별 어댑터가 맡고, 순서 대조·상태·결과 저장은 공유한다. 기록용 DB·ORM·기록 서버는 필요하지 않다. 읽기 비교용 연결과 시험 쓰기용 연결은 명령 생성 단계부터 분리한다.

| 영역 | 초기 검증 목표안 | 지원을 확정할 증거 |
|---|---|---|
| 런타임·UI | .NET 10 LTS, 구현 시작 시 확인한 Avalonia 안정판 | SDK·패키지 버전 고정, 두 OS 빌드·실행 |
| macOS | macOS 26 arm64, 실제 M4 Pro 환경 우선 | 배포 묶음의 첫 실행·전체 비교·취소·보안 저장소 |
| Windows | Windows 11 24H2 이상 x64 우선 | 실제 Windows 호스트에서 동일 검사·배포 확인 |
| SQL Server | SQL Server 2022, Microsoft.Data.SqlClient | catalog·자료형·권한·TLS·시험 DB 검증 |
| PostgreSQL | PostgreSQL 17, Npgsql | 논문 사례와 일반 자료형·권한·TLS 검증 |
| MySQL | MySQL 8.4, MySqlConnector | InnoDB·catalog·자료형·인증 검증 |
| MariaDB | MariaDB 11.4, MySqlConnector와 별도 catalog 어댑터 | MySQL과 다른 정의·권한·자료형 검증 |

이는 사용자 보유 DB 버전의 확정이나 제품 지원 완료 목록이 아니다. 다른 버전·Windows ARM64·macOS x64는 실제 확인 후 범위를 추가한다. 같은 DBMS의 서로 다른 버전도 기능별 사전 확인을 수행하며, 검증하지 않은 해석은 해당 항목을 확인 불가로 둔다. MySQL과 MariaDB를 서로 같은 DBMS로 취급하지 않는다. DB 서버 OS는 앱 OS와 같을 필요가 없다.

2026-10-01 확인 근거: [.NET 지원 정책](https://learn.microsoft.com/en-us/dotnet/core/releases-and-support), [Avalonia 플랫폼](https://docs.avaloniaui.net/docs/supported-platforms), [MySqlConnector](https://mysqlconnector.net/). 정확한 패치·패키지 버전은 구현 단계에서 고정한다. 프레임워크의 지원 목록을 이 앱의 실행 증거로 대신하지 않는다.

## 접속과 관측 범위

1. 원본·대상마다 DBMS, 서버·포트, DB 이름, 인증 방식, 계정, TLS·인증서, 연결·명령 제한 시간을 입력한다. 사용자 값을 연결 문자열에 단순 이어 붙이지 않고 드라이버의 연결 설정 객체로 구성한다. 잘못된 주소·포트·암호·인증서를 입력하면 해당 연결의 안내를 표시하고 수정할 수 있게 한다.
2. 기본 인증 목표는 각 DBMS의 계정·비밀번호 방식이다. SQL Server 통합 인증, PostgreSQL 통합 인증, 클라우드 토큰 등은 드라이버·OS·서버 설정별 실제 시험 후 지원으로 표시한다. 앱 자체 계정 가입은 없다. 검사 계정 하나로 정의를 읽는 것과 다른 DB 사용자의 실제 인증·동작을 검증하는 것은 구분한다.
3. TLS 기본은 인증서와 서버 이름 검증이다. PostgreSQL·MySQL 계열은 VerifyFull, SQL Server는 암호화와 인증서 검증을 사용한다. 인증서 오류가 나면 연결을 실패시키며 암호화 해제·인증서 무시로 자동 재시도하지 않는다. 개발용 예외 옵션을 넣는다면 사용자가 직접 선택한 제한 설정을 실행 전에도 표시한다.
4. 실제 연결된 DBMS·버전·DB와 접속 범위를 확인한다. 원본과 대상을 바꿔 연결했거나 같은 DB를 양쪽에 넣은 경우를 안내한다. 검사 중 재접속·복제본 전환으로 관측 DB가 달라지면 중단한다. 자동으로 이어서 결과를 합치지 않는다.
5. catalog 목록, 정의 가시성, 테이블 SELECT, 사용자·권한 조회, 행 필터·마스킹, 자료형 지원을 항목별로 조사한다. 능력 상태는 가능·일부 가능·추가 준비 필요·확인 불가다. 관리 권한 전체를 일괄 요구하거나 자동 부여하지 않고 필요한 조회 권한과 이유만 안내한다.
6. 객체 목록의 완전성은 종류별로 완전·부분·확인 불가를 기록한다. 조회가 비어 있다는 사실만으로 객체가 없다고 결론내리지 않는다. 상대편 객체 누락 판정은 그 종류의 목록 가시성이 충분할 때만 한다. 확인할 수 있는 차이는 먼저 보고하고 불확실한 영역도 함께 남긴다. SQL Server의 제한된 metadata 조회는 빈 결과를 줄 수 있으므로 특히 가시성 근거를 따로 확인한다. [Metadata 가시성](https://github.com/MicrosoftDocs/sql-docs/blob/live/docs/relational-databases/security/metadata-visibility-configuration.md)

접속 근거: [SqlClient 연결 옵션](https://learn.microsoft.com/en-us/dotnet/api/microsoft.data.sqlclient.sqlconnection.connectionstring?view=sqlclient-dotnet-standard-5.1), [Npgsql 보안](https://www.npgsql.org/doc/security.html), [MySqlConnector 연결 옵션](https://mysqlconnector.net/connection-options/). SQL Server의 ApplicationIntent=ReadOnly는 연결 라우팅 설정이며 쓰기를 막는 보안 장치로 사용하지 않는다. [읽기 라우팅 설명](https://learn.microsoft.com/en-us/sql/connect/ado-net/sql/sqlclient-support-high-availability-disaster-recovery?view=sql-server-ver17)

## 원본·대상에 보내는 명령의 경계

읽기 비교는 앱이 정의한 catalog 조회와 선택한 기본 테이블 SELECT만 실행한다. 매개변수 값은 바인딩하고 식별자는 DBMS 규칙으로 인용한다. 사용자 SQL, 프로시저 호출, view 실행, 시퀀스 값 발급, DDL·DML·권한 변경은 이 경로에 넣지 않는다. 계산 컬럼·외부 테이블·사용자 정의 변환처럼 조회 자체가 사용자 코드를 실행할 수 있는 경로는 안전한 관측 방법이 확인되기 전까지 해당 값 검사를 확인 불가로 둔다. 객체 정의 비교는 계속할 수 있다.

| DBMS | 관측 방법과 제한 |
|---|---|
| PostgreSQL | READ ONLY·REPEATABLE READ 트랜잭션으로 기본 테이블을 읽는다. row_security=off는 정책 우회가 아니라 필터 적용 시 오류를 내도록 사용하는 설정이다. 오류를 전체 행 일치로 바꾸지 않는다. 시스템 함수·catalog는 schema를 명시한다. |
| SQL Server | 이미 사용 가능한 SNAPSHOT을 우선 사용한다. 앱이 DB 옵션을 켜지 않는다. 없으면 사용자가 쓰기를 멈춘 조건에서 읽고 관측 방식의 제한을 기록한다. NOLOCK은 사용하지 않는다. RLS가 전체 행 관측을 제한하거나 UNMASK가 없어 값이 가려지면 전체 값 비교를 판정하지 않는다. |
| MySQL·MariaDB | 지원되는 엔진에서 READ ONLY·일관 snapshot을 사용한다. InnoDB와 다른 저장 엔진을 구분한다. snapshot 보장이 확인되지 않은 엔진은 정지 조건과 제한을 명시한다. 전역 설정 변경·테이블 잠금·DDL을 실행하지 않는다. |

두 DB의 snapshot은 서로 독립적이다. 쓰기 정지 확인은 사전 조건이며, 앱이 모든 동시 변경을 탐지하거나 두 서버의 동일 시점을 보장한다고 표현하지 않는다. 정의·접속 대상의 전후 변화 등 실제 관측된 변경은 판정 불가 사유로 남긴다. 암호화 컬럼을 복호화할 수 없으면 암호문 비교를 원래 값 비교로 표시하지 않는다. DB 자체의 감사·접속 기록까지 무변경이라고 보장하지 않는다.

근거: [PostgreSQL 트랜잭션](https://www.postgresql.org/docs/17/sql-set-transaction.html), [row_security 설정](https://www.postgresql.org/docs/17/runtime-config-client.html), [SQL Server RLS](https://learn.microsoft.com/en-us/sql/relational-databases/security/row-level-security?view=sql-server-ver17), [마스킹·UNMASK](https://learn.microsoft.com/en-us/sql/relational-databases/security/dynamic-data-masking?view=sql-server-ver17), [MySQL 트랜잭션](https://dev.mysql.com/doc/refman/8.4/en/commit.html), [MariaDB 트랜잭션](https://mariadb.com/docs/server/reference/sql-statements/transactions/start-transaction).

전체 선택이면 사용자 schema와 발견된 관련 DB 객체가 기본 대상이며 논문에 없던 특수 객체도 목록에서 사라지지 않게 한다. 외부 연결·확장·암호화 객체 등 아직 해석할 수 없는 항목은 종류와 미검증 이유를 남긴다. 서버 검사 범위는 선택 DB에 관련된 계정 연결·권한·설정이며 다른 DB 전체나 OS를 검사하지 않는다.

테이블·컬럼은 schema를 포함한 같은 이름으로 자동 대응하고 사용자가 일대일 대응을 바꿀 수 있다. 중복 대응과 다른 대상 컬럼으로의 충돌을 금지한다. 누락·추가·이름 변경은 구조 차이로 남기며 대응 지정은 값 비교를 가능하게 할 뿐 정의 차이를 숨기지 않는다. 자료형 차이가 있으면 이를 보고하고 손실 없는 값 비교가 가능한 컬럼만 추가 대조한다. 변환 규칙으로 값 차이를 승인하지 않는다.

사용자·역할·소유자는 같은 이름으로 대응한다. MySQL 계열 계정은 이름뿐 아니라 host 범위를 포함한다. 함수는 schema·이름·인자 signature로 구분하고 FK 참조는 schema·테이블·컬럼 순서를 포함한다. SQL Server의 로그인-사용자 연결은 관련 SID와 연결 상태도 검사하며, SID 차이를 무조건 로그인 실패라고 단정하지 않는다. 암호·인증 hash·비밀 설정값은 비교 대상에서 제외하고 인증 성공을 검증한 것으로 표시하지 않는다.

정의는 서버가 제공하는 형식과 확인된 속성을 비교한다. 의미가 같아 보인다는 이유로 SQL 공백·식·객체명을 임의 재작성하지 않는다. 동적 SQL의 실제 참조, 외부 인증 그룹의 전체 멤버십, 서버 밖 실행 동작은 catalog만으로 입증하지 않는다. 선언된 의존 관계와 실제 실행 검증을 구분한다. 논문 과제의 고정 변환·고정 역할명을 기본 판정 규칙에 넣지 않는다.

## 엄격한 값 비교

비교 대상은 DB가 저장하고 관측할 수 있는 타입별 값이다. 물리 DB 파일·삭제 공간·저장 전 입력 문자열의 동일성을 보장하는 검사가 아니다. 타입 태그·NULL 표식·길이를 포함한 모호하지 않은 비교 표현을 만들고 codec 버전을 기록한다. 일반 ToString·문화권 설정·부동소수점 변환에 의존하지 않는다.

| 값 종류 | 대조 조건과 손실 방지 |
|---|---|
| NULL·문자·binary | NULL과 빈 값, 공백·대소문자·Unicode 차이, byte 차이를 그대로 구분. trim·case-fold·Unicode 정규화·DB collation 동등 비교 금지. 고정 길이 문자 padding의 실제 관측을 DBMS별 시험 |
| 정수·정확한 소수 | 부호·정수·소수 값을 손실 없이 대조. .NET decimal 범위를 넘으면 임의 정밀도 표현 사용. 1과 1.0의 동일 수치와 컬럼 scale 정의 차이를 분리. 반올림·epsilon 금지 |
| float·특수 수치 | DB에서 보존해 전달하는 정밀도의 표현을 대조. 근사 허용 없음. NaN·무한대·음의 0의 보존 여부를 DBMS별 시험하고 보존을 입증하지 못한 경우 판정 불가 |
| 날짜·시간·interval | DB 정밀도·범위·시간대 타입을 보존. UTC instant 타입과 offset 저장 타입 구분. 초 미만 손실·범위 초과·월 포함 interval·MySQL zero date를 일반 DateTime으로 강제 변환하지 않음 |
| JSON·XML | 텍스트로 저장되는 값은 관측 문자열을 그대로 대조. DB가 정규화해 저장한 native JSON은 해당 타입의 손실 없는 관측 표현을 대조. 숫자를 double로 재파싱하거나 NULL/JSON null/키 없음·배열 순서를 혼동하지 않음 |
| UUID·배열·범위·domain·공간·확장 | 타입 전용 codec으로 길이·차원·경계·NULL 요소 등 보존. codec이 없거나 충실한 변환을 입증하지 못하면 해당 컬럼 미검증. 문자열 fallback으로 통과 금지 |

드라이버 검증 근거: [Npgsql 자료형과 순차 읽기](https://www.npgsql.org/doc/types/basic.html), [MySqlDecimal](https://mysqlconnector.net/api/mysqlconnector/mysqldecimaltype/). MySQL zero date는 원래 표현을 보존하며 DateTime.MinValue로 치환하지 않는다. 타입별 반례는 [인수 기준](requirements.md)에 연결한다.

행 순서는 데이터 차이가 아니다. 관측되는 저장 문자·시간·정확한 수치의 차이는 숨기지 않는다. 값과 함께 타입 정의를 검사하므로 값은 같고 타입은 다른 결과를 별도로 표시할 수 있다.

## 행 대응과 대용량 처리

1. 선택 컬럼을 순차 읽기로 나눠 읽는다. 컬럼 하나가 메모리 예산보다 커도 LOB를 스트림으로 처리한다. 전체 행을 메모리에 수집하거나 페이지 OFFSET으로 건너뛰며 전체 검사를 흉내내지 않는다.
2. 양쪽에서 사용할 수 있는 PK 또는 NULL 없는 유일 키를 후보로 삼되 실제 값의 중복도 확인한다. DB collation의 정렬 순서를 공통 정렬로 믿지 않고 타입별 비교 표현으로 로컬 외부 정렬한다. 같은 키의 컬럼별 차이를 보고한다.
3. 유효 키가 없거나 중복 키를 만나면 전체 행의 다중집합 비교를 사용한다. 모든 컬럼이 같은 행의 출현 개수까지 대조한다. 임의로 두 행을 짝지어 특정 컬럼이 수정됐다고 말하지 않고 원본에만/대상에만 관측된 행·중복 개수 차이로 보고한다.
4. 메모리 예산 안에서 정렬한 조각을 보호된 임시 파일에 쓰고, 병합하면서 양쪽 값을 정확히 대조한다. 해시는 후보 묶기·무결성 보조 수단이다. 최종 일치는 실제 비교 표현 전체의 대조로 결정한다. 해시 충돌 반례에서도 차이를 놓치면 안 된다.
5. partition 부모를 읽어 포함된 자식의 행을 다시 합산하지 않는다. 자식만 선택하는 범위도 명시한다. DB별 temporal/history 등 별도 저장 대상은 발견 목록과 검사 선택에 드러낸다.
6. 초기 자원 설정 제안은 비교 버퍼 256 MiB이며 사용자 조정과 OS 상태를 반영한다. DB 크기·행 개수의 임의 상한은 두지 않는다. 큰 셀·정렬·결과 저장도 이 예산을 지키도록 구현한다. 임시 공간은 입력 크기·정렬 단계에 따라 늘어나며 부족하면 판정 불가로 끝난다. 정해진 시간이나 무한 자원을 약속하지 않는다.
7. 결과도 순차 기록하고 화면은 페이지·가상 목록으로 표시한다. UI 표시 제한을 실제 검사·발견 기록의 생략으로 바꾸지 않는다. 총량을 모르면 처리 행·bytes·현재 단계로 진행을 표시하며 근거 없는 완료 백분율을 만들지 않는다.

선택 범위를 완전히 읽고 codec·정렬·병합·중복 개수·완료 기록을 확인해야 DATA-01을 일치로 확정한다. 알려진 불일치는 중간에 발견해도 보존할 수 있으나 그 시점의 결과를 전체 완료라고 표시하지 않는다.

## 임시 저장과 로컬 결과

임시 값 저장은 검사별 전용 디렉터리에서만 한다. Unix는 소유자 전용 디렉터리/파일 권한, Windows는 현재 사용자 접근 ACL을 적용하고 실패 시 해당 처리 경로를 중단한다. 운영체제의 표준 암호화 구현으로 검사마다 새 키를 만들고 인증된 암호화로 조각을 보호한다. 키는 검사 프로세스 메모리에만 둔다.

조각 번호·길이·건수·타입/codec·검사 ID·완료 표식이 있는 manifest도 인증한다. 조각 삭제·재배열·변조·미완료 저장을 확인하며, 정렬/병합을 다시 읽을 때 검증한다. 손상·디스크 부족·flush 실패는 해당 검사의 판정 확정을 막는다. 이것은 임시 자료의 보호이며 원 DB의 정확성 증명이 아니다.

취소·정상 종료 때 앱 소유 자료를 정리하고 다음 시작에 소유 표식이 확인되는 잔여 디렉터리를 정리한다. 링크·경로 바꿔치기로 다른 자료를 지우지 않는다. 소유가 불명확하거나 삭제가 실패하면 남은 임시 자료를 안내한다. 재시작 후 잃은 키를 복구하거나 임시 값을 결과 파일에 넣지 않으며 중단 자료로 이어하기를 제공하지 않는다. 저장장치에서의 복구 불가능한 완전 삭제를 보장하지 않는다.

영구 결과는 버전이 있는 로컬 파일에 안전한 결과만 저장한다. 임시 파일에 완전히 저장·검증 후 교체하고 손상·미지원 버전이면 다시 열기 오류를 표시한다. 설정·검사 범위·안전한 판정과 finding ID, 미검증 이유, 앱/어댑터/codec 버전을 보관한다. CSV·HTML도 같은 안전한 결과 모델을 사용한다. HTML은 문자열 escape, CSV는 spreadsheet 수식 실행 방지를 적용한다.

실제 행 값·PK·원 SQL 정의·비밀번호·토큰·인증 hash·매개변수·원본 예외 문자열은 결과/로그에 쓰지 않는다. 계정·역할·기타 객체의 차이는 내부 식별번호와 차이 종류로 표시한다. 테이블·컬럼 위치는 확정 정책에 따른다. 드라이버 오류는 안전한 오류 코드·분류로 변환한다. 비밀번호의 선택 저장은 macOS Keychain·Windows 보안 저장소로 구현하고 일반 파일에는 참조만 둔다. 민감한 접속 정보는 기본 메모리 보관하며 저장 범위는 화면에서 명시한다.

## 별도 시험 DB의 동작 시험

사용자가 변경 가능한 시험 DB를 준비한다. 앱은 해당 DBMS의 준비 절차, 필요한 구조·계정·권한과 변경 가능성을 안내한다. 앱이 clone·백업 복원·전체 초기화를 실행하지 않는다. 시험 DB가 대상 DB와 같은 구조/설정을 가졌는지 확인 가능한 항목을 대조해 어느 환경에서의 결과인지 기록한다. 시험 DB의 성공을 대상 DB의 실제 동작 성공으로 승격하지 않는다.

쓰기 시작 전에 실제 서버·DB 식별과 접속 경로를 확인해 원본·대상과 분리된 DB인지 판별한다. 동일 DB의 별칭, 다른 포트/호스트명, 복제/라우팅 경로만으로 별도 공간이라 믿지 않는다. 분리를 확인하지 못하면 쓰기를 실행하지 않는다. 백업 복원으로 내부 ID가 같은 경우도 고려해 DBMS별 판별을 시험한다.

기본 시험안은 선택한 테이블의 타입·NULL·키·FK·CHECK·기본값·identity 등을 입력으로 만든다. 사용자는 시험 값과 기대 결과를 실행 전에 확인한다. 생성값의 의도나 업무 규칙은 임의 추론하지 않는다. 복잡한 제약·사용자 함수·참조 데이터처럼 자동 생성하지 못한 항목만 추가 입력받거나 미실행으로 남긴다.

진행은 입력 → 읽어 확인 → 앱 생성 행 수정 → 읽어 확인 → 앱 생성 행 삭제 → 정리 확인이다. FK 부모 자료를 먼저 준비하고 의존 순서를 고려한다. 허용 입력과 거부 입력을 분리하고 예상 위반의 오류 종류·제약·발생 단계를 확인한다. 권한 부족·연결 실패·다른 제약 오류를 의도한 입력 거부의 성공으로 처리하지 않는다. COMMIT 시점의 지연 제약과 트랜잭션 중단 상태도 다룬다.

기존 행은 시험 수정·삭제의 대상이 아니다. 앱이 방금 생성한 행을 정확한 식별과 실행 기록으로 추적하며, 소유를 입증하지 못하면 변경·정리를 보류한다. 공통 접두사나 ID 범위만으로 삭제하지 않는다. sequence 소모·trigger·감사 기록 등은 ROLLBACK이나 입력/수정/삭제 순서만으로 되돌아간다고 보장하지 않는다. 남은 변경·정리 실패·확인 불가 부분을 [확정 정리 정책](../RULE.md)에 따라 따로 보고한다.

역할 동작 시험은 별도 공간에서 실제 허용/거부를 관측할 수 있는 계정 또는 검증된 impersonation 방식으로 수행한다. 필요한 경우 선택한 시험 계정 정보만 받는다. 모든 사용자 비밀번호는 필요하지 않지만 catalog 비교만으로 각 사용자의 실제 로그인 성공을 주장하지 않는다. 업무 API·부하·마이그레이션 도중 중단 등의 운영 시험은 실행 목록에 넣지 않는다.

## 결과·중단 모델

각 검사 기록은 run ID, 검사 ID, 선택 범위, 연결/관측 방식, capability, 실행 상태, 판정, 안전한 finding ID·위치·종류, 이유 코드와 연구 RP 연결을 가진다. 실제 값이나 행 키를 finding ID로 인코딩하지 않는다. 종료 시간과 관측한 범위, 전체 완료 여부를 명시한다.

| 상황 | 표시·집계 |
|---|---|
| 선택 필수 항목이 모두 완료·일치, 누락/확인 불가 없음 | 선택 범위 내 일치. 선택 제외 범위는 별도 명시 |
| 확정된 차이가 있음 | 불일치 발견과 차이 개수. 다른 미검증·중단 영역도 동시에 표시 |
| 차이는 아직 없지만 완전 관측/비교를 못 함 | 판정 불가/미검증 영역 있음. 전체 일치 금지 |
| 선택하지 않음 | 선택 안 함. 검사 성공 건수에 포함하지 않음 |
| 버전·객체 종류에서 기능이 없음을 확인 | 적용 대상 아님. 지원 구현 누락·권한 부족에 쓰지 않음 |
| 사용자 취소·timeout·연결 종료·임시 자료 실패 | 완료/중단/미시작 분리. 새로운 run ID로 전체 재검사만 제공 |
| 원본·대상 모두 같지만 원본 제약 위반 근거가 있음 | 일치 여부와 '원본에 존재하는 결함'을 병기 |
| 시험 기대 결과 충족, 정리 실패 | 기대 충족과 정리 실패·남은 변경을 병기 |

이유 코드는 권한 부족, 목록 가시성 불명, 행 필터, 마스킹/복호화 불가, 타입/버전 미검증, 정의 조회 불가, 관측 중 변경, 취소, 연결 끊김, 시간 초과, 임시 무결성 실패, 저장 공간 부족, 시험 DB 분리 불명 등으로 구분한다. 진행 중 예외는 범위에 맞춰 처리하되 전역 연결·snapshot·임시 신뢰가 깨지면 관련 진행 검사를 중단한다. 영향 없는 완료 결과를 지우거나 미시작을 실패로 꾸미지 않는다.

DBMS RadioButton·범위/테이블 CheckBox와 동작 줄이기는 native 의미·키보드 조작을 유지한다. 당시에는 기본 선택만 있었고 카드·검색·일괄 선택·수치 행은 후속이었다. 이후 UI-ALIGN-01에서 카드·검색·일괄 선택·수치 행을 실제 구현했다. 수동 대응은 여전히 미구현이다. 이 차이를 기능이 완성된 것처럼 감추지 않는다. 진행 행 카운터는 페이지를 다시 만들거나 전환 애니메이션을 반복하지 않는다. 결과 수치는 최종 실제 숫자이며 한 검사에 차이와 불확실 범위가 공존하면 양쪽 수치에 포함된다는 설명을 둔다.

화면 초안의 첫 도움 문장·세 행동, 대분류/세부 펼침, 대응 편집, 제한 안내와 결과 읽기 순서는 위 화면 시안 구성이 정본이다. C#·Avalonia 구현에서 실제 비교 엔진과 연결하고 UI-01–UI-04를 다시 확인한다. 지원 목표의 실제 시험 환경·성능·패키지 서명은 [현재 상태](status.md)에 추적한다. 여기의 기술 기본값은 구현 때 시험하며 결과에 따라 근거와 함께 수정한다.

## IMPLEMENTATION-02 · 결과 보관 수정

2026-10-02 JSON 재열기와 CSV·HTML 내보내기를 같은 안전한 결과 모델에 연결했다. 형식별 native 저장 dialog를 거쳐 명시적으로 경로를 선택하며 여러 형식 중 취소/실패는 완료 형식을 보존·표시한다. ## IMPLEMENTATION-02 · 수동 대응과 PostgreSQL 구조 비교

같은 이름 자동 대응에 일대일 테이블/컬럼 selector를 추가했다. 검색·현재 선택·사용 중 대상의 비활성 이유·대응 없음, 취소/Escape 초안 폐기와 적용 후 검사 전 요약을 연결했다. 키보드 Enter/Space는 key-up에서 한 번 실행하고 호출 버튼으로 초점이 돌아온다. 새 대상은 컬럼 초안을 다시 만들며 이미 사용 중인 대상은 중복 선택할 수 없다. 적용은 값 변환 승인이 아니며 미대응 컬럼은 데이터 전체 일치를 차단한다. 형식 2 JSON에 실제 선택 대응을 보존하고 형식 1도 계속 읽는다.

사전 확인/분류 펼침은 실제로 수집한 구조 검사별 테이블 수와 미관측 경계를 표시한다. SCHEMA-01/02/03은 선언·catalog 상태를 비교하고 원본 제약 위반 및 실제 실행과 구분한다. 속성별 한영 finding을 같은 안전한 결과 모델/CSV/HTML에 사용한다. 새 selector·펼침·저장은 기존 버튼 높이/위계·실행 Pulse·dialog/notice 애니메이션·동작 줄이기를 유지한다. 실제 범위와 증거/남은 인수는 [구현 검토](implementation-review.md)를 따른다.
