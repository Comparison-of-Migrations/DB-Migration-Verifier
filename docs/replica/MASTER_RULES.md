# Web → C# Avalonia 복제 작업 규칙

2026-10-02 사용자 확정. 이 문서는 복제 방법의 정본이다. 제품·DB 보호 정책은 [RULE](../../RULE.md), 작업 진입점은 [AGENTS](../../AGENTS.md)다.

## 최종 목표

대상 웹의 UI, 레이아웃, 상태 변화, 인터랙션, 크기 관계를 가능한 한 그대로 C# + Avalonia로 복제한다. 임의 재해석·디자인 개선·구조 변경보다 **원본 웹과의 일치도**를 최우선으로 한다. Windows/macOS 데스크톱 범위다.

## 1. Bottom-Up 구현

Primitive → Atomic Component → Composite Component → Section → Page → Application 순으로 진행한다. 가장 작은 내부 컴포넌트부터 조사·검증한다. 상위 컴포넌트를 대충 만든 뒤 내부를 채우지 않는다. 기존 앱에 상위 화면이 있다는 사실은 하위 컴포넌트 검증 완료를 뜻하지 않는다.

## 2. 시작 전 원본 확인

각 컴포넌트 작업 직전에 실행 중인 대상 웹의 해당 부분을 다시 확인한다. 기존 Avalonia 구현으로 원본을 추측하지 않는다.

- DOM 구조, 직접적인 부모/자식 관계와 데이터에 따른 상태 변화
- 실제 크기, padding/margin/gap, 정렬, 색상, border/radius, font/icon
- hover/pressed/selected/disabled/focus와 animation/transition

원본 CSS 선언뿐 아니라 최종 computed style과 실제 배치를 기록한다. 덮어쓴 CSS·숨겨진 요소·줄바꿈·크기 관계를 누락하지 않는다. 미확인 값은 추측해서 채우지 않고 미확인으로 남긴다.

## 3. 한 번에 하나의 컴포넌트

원본 조사 → 구조 기록 → Avalonia 구현 → 원본 비교 → 차이 수정 → 완료 판정 → LOCK 순으로 진행한다. 2026-10-08 사용자 병렬 지시에 따라 활성 작업은 **에이전트별 하나**만 둔다. root가 [COMPONENT_STATUS](COMPONENT_STATUS.md)에 담당자별 활성 작업을 반영하고 각 에이전트는 `workers/<담당자>/STATUS.md`에 현재 단계와 복구 경로를 기록한다. 파일 소유권·공유 검증 환경 차례는 [PARALLEL_WORK](PARALLEL_WORK.md)를 따른다. 전체 작업을 end-to-end로 마칠 때까지 단위 완료를 대화 종료로 취급하지 않는다. 검증·LOCK 기록 후 다음 의존 작업을 자동으로 진행하고, 사용자 입력이 반드시 필요한 실제 blocker에서만 중단한다. 새 단위마다 승인을 요구하지 않는다. 작업 중 다른 컴포넌트의 디자인·구조를 임의 변경하지 않는다. 작업 종료·중단 전에 현재 차이·증거·다음 행동을 현재 명세와 상태에 기록한다.

## 4. LOCK

검증한 컴포넌트만 `LOCKED`로 표시한다. LOCK 이후 임의 리팩터링·디자인·크기·구조·스타일 재해석을 금지한다. 상위 컴포넌트 조립에 변경이 반드시 필요할 때만 예외를 허용한다.

수정 **전에** 해당 명세의 LOCK 변경 기록에 ① 변경 이유 ② 영향받는 컴포넌트 ③ 원본 웹 근거를 기록한다. 이전 검증을 그대로 유효하다고 주장하지 않는다. 변경 범위와 영향받는 부모/자식을 다시 대조한 후 잠근다. 해당 에이전트는 변경 중 다른 컴포넌트 구현을 동시에 시작하지 않는다. 다른 에이전트도 그 파일·LOCKED 범위를 변경하지 않는다.

## 5. 맥락 압축·기억 불확실 시 복구

기억이나 요약만으로 구현을 계속하지 않는다. 새 작업·맥락 압축·중단·상세 기억 불확실 시 다음 순서를 실제로 수행한다.

1. AGENTS와 이 MASTER_RULES를 읽는다.
2. COMPONENT_STATUS와 PARALLEL_WORK/HEADLESS_VERIFICATION, 자기 workers 상태에서 담당 활성 컴포넌트·현재 단계·다음 행동·환경 사용 차례를 읽는다.
3. 활성 컴포넌트의 `specs/<Component>.md`를 읽는다.
4. 현재 컴포넌트와 직접 관련된 원본 웹 코드 및 실행 상태를 다시 확인한다.
5. 해당 Avalonia 구현을 확인한다.
6. 명세의 기존 결정·현재 차이와 실제 구현을 대조한다.
7. 기록한 단계부터 재개한다.

복구 확인 사실은 활성 명세의 재개 기록에 짧게 남긴다. 압축은 설계 초기화가 아니다. 확정된 결정을 재해석하거나 설계를 다시 시작하지 않는다.

## 6. 전체 재분석 금지

압축만을 이유로 전체 웹을 처음부터 다시 분석하지 않는다. 현재 컴포넌트와 직접적인 부모/자식만 조사한다. 이미 LOCKED인 컴포넌트는 기존 명세를 조립 계약으로 사용한다. 실제 원본 변경 증거가 발견되면 영향을 받는 부분만 차이를 기록한다.

## 7. 지속 기록과 정본 역할

| 문서 | 역할 |
|---|---|
| MASTER_RULES.md | 복제 규칙 |
| COMPONENT_STATUS.md | 컴포넌트 현재 상태·활성 작업·다음 행동 |
| COMPONENT_TREE.md | 의존 관계·원본 위치·기존 구현 위치 |
| specs/<Component>.md | 원본 DOM/CSS·크기·spacing·typography·상태·interaction·부모 관계·Avalonia 구조·구현 파일·검증 결과·알려진 차이·LOCK 기록 |
| screenshots/ | 원본/구현 비교 캡처. 환경·상태는 해당 명세에서 연결 |
| source/manifest.json | 실행 중인 원본 캡처 환경·코드 해시 |

각 사실은 위 역할의 한 곳에 기록하고 다른 문서는 링크한다. 긴 과거 일지를 현재 상태로 복사하지 않는다. 캡처에는 실제 개인정보·비밀값을 넣지 않는다.

## 8. 충돌 시 우선순위

1. 실제 실행 중인 원본 웹
2. 원본 DOM/CSS/JS
3. COMPONENT_SPECS (`specs/`)
4. 현재 Avalonia 코드
5. 모델의 추론

모델의 기억·일반 UI 관례로 원본을 변경하지 않는다. 소스 파일과 로드된 웹이 다르면 먼저 양쪽을 보존하고 차이를 기록한다. 임의로 파일 버전을 복제 기준으로 승격하지 않는다. 원본 수정 초안은 `source-candidates/`에 구분해 보관한다.

## 9. 임의 개선 금지

- “Avalonia에서 더 자연스럽다”는 이유로 변경하지 않는다.
- 일반 UX 관례 적용·비슷한 색/spacing 대체·구조 단순화를 하지 않는다.
- 원본에 없는 hover/animation을 추가하지 않는다.
- 원본의 이상한 동작을 임의로 고치지 않는다.

기존 brief/tokens·UI-01–UI-04는 원본 확인 항목이다. 원본과 충돌할 때 새 디자인을 만드는 근거로 쓰지 않는다. 충돌을 명세에 기록한다. 실제 DB 보호·비밀값 비노출 정책은 유지한다. 시안의 예시 성공을 실제 검사 성공으로 가장하지 않는다. OS 파일 대화상자·실제 데이터/지원 범위 등 대응이 필요한 차이는 별도 항목으로 기록하고 임의 면제하지 않는다.

## 10. 상위 컴포넌트 조립

직접 하위 컴포넌트가 모두 LOCKED인 이후에만 상위를 작업한다. 상위에서는 가능한 한 잠긴 컴포넌트를 조립한다. 현재 의존 순서는 COMPONENT_TREE를 따른다. 컴포넌트 경계의 수정도 원본 근거를 먼저 기록한다.

## 11. 완료·LOCK 조건

다음 모두를 원본과 비교하고 증거를 연결한 뒤에만 LOCKED로 변경한다.

- 구조, 크기, 위치, spacing
- typography, 색상, border/radius
- 상태별 UI, interaction, 부모 안 배치

적용되는 모든 상태·언어·창 크기에 대해 검증 범위와 미확인 범위를 명시한다. 빌드 성공·이전 전체 페이지 캡처·문서 작성만으로 LOCK하지 않는다. 알려진 구현 차이/미확인 항목이 남으면 완료로 승격하지 않는다. 아래 OS 기본 표현 차이 판정을 적용한 항목은 기록을 보존한 채 완료할 수 있다. 적용되지 않는 항목은 원본 근거와 이유를 적는다.

## 12. OS 기본 설정에 의한 차이 허용 · 2026-10-08 사용자 추가

사용자 지시: “기본설정인데, os인해서 다른부분은 억지로 맞추지 않아도 좋다.”

기본 글꼴의 래스터화/안티앨리어싱, OS 스크롤바 표현, 파일 대화상자와 창 장식 등 운영체제·기본 렌더러가 만든 차이를 강제로 복제하기 위한 추가 보정은 요구하지 않는다. 해당 컴포넌트 명세에 원본/후보 환경, 차이의 범위, 확인 근거와 기능 영향 여부를 기록한다. 기하·색상·데이터·동작이 일치하고 기본 표현 경계에만 남는 차이는 `허용된 OS 표현 차이`로 명시하고 LOCK할 수 있다. 이미 통과한 코드를 이 조건만으로 다시 바꾸지는 않는다.

운영체제 때문인지 확인하지 못한 차이, 앱 구현 누락, 잘못된 크기/정렬/배치, 잘못된 입력/판정/상태 전환은 이 예외에 포함하지 않는다. 원본 앱 정책과 부모/자식 계약은 계속 복제한다. 이전의 ‘모든 차이를 해결’ 문구와 충돌하면 이 최신 사용자 조건이 우선한다.

## 임시 재개 제약의 수명

진행 중인 복제 작업의 압축 후 상기 의무는 AGENTS에 연결한다. 전체 컴포넌트 조립·원본 비교·남은 차이 검증이 끝난 뒤에만 진행 중이라는 임시 절을 제거한다. 턴 종료·일부 LOCK은 제거 조건이 아니다. 이 사용자 확정 규칙·명세·증거는 완료 뒤에도 보존한다.

**추측하지 말고 원본을 확인한다. 이미 확정된 것을 다시 설계하지 않는다. 작은 컴포넌트부터 검증하고 잠근 뒤 위로 조립한다. Context Compression은 설계를 초기화하는 이벤트가 아니다.**

## 검증 운영 최신 추가 · 2026-10-08
사용자의 Headless 병렬 및 실제OS 분리 조건은 [HEADLESS_VERIFICATION](HEADLESS_VERIFICATION.md)를 정본으로 적용한다. 독립 source/build/process/render/evidence, HEADLESS_PASSED≠LOCK, 실제Mac/Windows자원별순차, 통과조건의 불필요한 반복금지. 이 절은 이전 단일전체환경 lease 안내보다 우선한다. 기존 원본우선/Bottom-Up/단일활성per-agent/LOCK보호는 유지한다.

## 13. 페이지 완성 → 실제 앱 연결 → 사용자 흐름 검증 · 2026-10-08

현재 계획은 기존 상태·의존·증거를 이어 사용한다. 원본 우선·Bottom-Up·에이전트별 단일 활성·LOCK 보호·제품 정책과 필수 검증은 유지한다.

독립 상태·동작·재사용 필요가 없는 텍스트와 장식은 부모 범위에서 구현·검증한다. 독립 컴포넌트를 추가할 때는 필요한 이유와 실제 사용 페이지를 명세에 적는다. 기존 LOCKED 하위는 그대로 재사용한다.

직접 하위가 LOCK된 페이지부터 완성한다. 완료 페이지를 기존 실행 앱에 단계적으로 연결하는 경우에 한해 전체 상위 LOCK 전 통합을 허용한다. 미완성 영역과 전체 앱은 미검증으로 유지하고 페이지 연결과 전체 흐름을 각각 확인한다. 예시 원본의 동작을 실제 DB 접속·검증 성공으로 표시하지 않는다.

동일 구현·환경·조건의 통과 증거는 재사용하고 새 동작·부모 배치·변경 영향·발견한 문제에 추가 검증을 집중한다. 적용되는 상태·언어·크기·실제 macOS/Windows 확인은 생략하지 않으며 headless만으로 LOCK하지 않는다.

기존 세 담당자는 독립 페이지 영역을 병렬 진행하고 root는 공유 파일·앱 연결·통합 검증을 담당한다. 파일 소유권과 실제OS 자원 차례는 계속 지킨다. COMPONENT_STATUS에는 페이지별 구현·앱 연결·흐름 검증을 분리한다. 압축 복구 시 활성 부모 범위와 통합 상태를 확인하며 단위 완료마다 멈추지 않는다. §1/§10의 전체 상위 잠금 전 조립 금지는 위 페이지 연결 예외에 한해 이 절이 우선한다.

## 14. 검증 완료 창 즉시 종료 · 2026-10-09

사용자 추가 조건: “검증이 끝난 컴포넌트 창은 반드시 종료한다.”

컴포넌트 검증 또는 해당 OS 검증 묶음이 끝나면 그 검증에 사용한 **프로젝트 소유 원본 측정 창·탭과 후보 컴포넌트 창을 바로 종료**한다. 다음 단계 대기·LOCK 문서 작성·상위 앱 연결을 이유로 완료 창을 남기지 않는다. Headless 검증 프로세스도 결과 저장 후 종료를 확인한다.

종료는 기존 소유 경로·PID·제목·자원 차례 guard를 유지하고, 사용자 원본 작업 탭이나 다른 앱은 닫지 않는다. 캡처·측정 결과·검증 기록을 먼저 보존하고, 정확한 창/프로세스 종료 확인을 각 담당자의 증거와 상태에 기록한 뒤 OS 자원을 반납한다. 검증 실패나 입력 실행 여부가 불확실하면 중복 입력 없이 진단·증거를 보존하고, 그 진단이 끝난 검증 창도 종료한다. 상위 앱이 별도 통합 검증 중이면 해당 범위만 계속 실행한다.
