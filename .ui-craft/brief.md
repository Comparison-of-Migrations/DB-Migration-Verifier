## 복제 작업의 우선 기준

2026-10-02 사용자 확정 [MASTER_RULES](../docs/replica/MASTER_RULES.md)를 따른다. 실행 중인 원본을 그대로 대조하며 이 문서의 일반 기준·기존 교정 값으로 원본을 개선하거나 다시 해석하지 않는다. 컴포넌트 진행은 [상태](../docs/replica/COMPONENT_STATUS.md)가 정본이다.

## 1. 제품 목적

마이그레이션이 끝난 원본·대상 DB를 상세 비교하고 차이와 확인하지 못한 영역을 보여주는 데스크톱 앱이다. 제품 정책의 정본은 [RULE](../RULE.md)이다.

## 2. 주요 사용자

Windows 또는 macOS 컴퓨터에서 별도 서비스 DB의 마이그레이션 결과를 확인하려는 개발자·DB 담당자다. 보유 권한의 범위를 미리 알지 못해도 접속 후 안내를 따라 검사할 수 있어야 한다.

데스크톱 전용 C#·Avalonia 앱이다. 브라우저는 화면 시안 검토 수단이다. 모바일 화면·모바일 검사 항목을 만들지 않으며, 창 크기·배율·마우스/키보드 조작을 기준으로 설계한다.

## 3. 설계 원칙

1. 확인하지 못한 부분은 일치로 표시하지 않는다. [판정 모델](../docs/product-design.md)을 따른다.
2. 중요한 다음 행동을 버튼의 위계와 배치로 드러낸다. [UI-01·UI-02](../RULE.md)를 따른다.
3. 누른 행동은 상태 피드백과 동작 애니메이션으로 인식시킨다. [UI-03·UI-04](../RULE.md)를 따른다.
4. 사용자 동의로 PlandoSee 테마 제약을 해제하고 후속 제안인 Discord 다크 테마를 참고한다. 탐색·작업·입력 영역을 서로 다른 짙은 회색으로 구분하고 핵심 행동과 선택에는 Blurple 강조색을 쓴다. DB 검증 흐름과 판정 의미에 맞춰 설계하며 구체적인 시안의 최종 승인은 사용자 검토 후 기록한다. 값은 [화면 토큰](tokens.md)을 따른다.

## 4. 화면 성공 조건

처음 온 사람이 1분 안에 도움 대상과 앱의 목적을 이해하고 다음 행동을 찾는다. 각 화면의 버튼 목록과 [DMV-12.1–DMV-12.4](../docs/requirements.md)의 실제 증거가 갖춰져야 화면 완료로 기록한다. HTML 시안의 검토 결과와 실제 Avalonia·첫 방문 사용자 검증을 구분한다. 최신 검증 상태는 [현재 상태](../docs/status.md)를 따른다.

## 5. 범위 경계

- 원본·대상 DB에 시험 쓰기나 마이그레이션을 실행하지 않는다.
- 실제 데이터 값·민감 행 키·비밀값을 결과에 노출하지 않는다.
- 일반 업무 백엔드·마이그레이션 중 운영 시험을 화면 범위에 추가하지 않는다.
- 애니메이션으로 기능 실행을 지연하거나 실제 완료 전 성공을 표현하지 않는다.

## 6. Learned constraints

- **2026-10-02 · 수직 정렬의 역할 구분** — 한 줄 조작 요소와 짧은 복합 셀은 전체 그룹 중앙, 여러 줄 설명·요약은 상단/첫 줄, 나란한 단계는 공통 행 시작선을 사용한다. 입력·선택 표시의 내부 정렬까지 실제 Avalonia에서 확인한다. *이유:* 고정 높이나 부모 정렬만으로 내부 글자/표시까지 맞는다고 가정해 전 페이지에 어긋남이 남았다. 근거와 실제 점검은 [수직 정렬 기록](../docs/ui-vertical-alignment.md)을 따른다.

- **2026-10-02 · 웹 시안과 실제 앱의 일치** — C#·Avalonia로 옮길 때 색만 맞추거나 기본 컨트롤/텍스트 목록으로 축약하지 않는다. 최신 웹 시안의 페이지 구조·위계·정렬·선택기·표·동작을 실제 native 화면에서 대조한다. *이유:* 첫 실행판에서 기능을 연결했지만 시안과 외형/흐름이 크게 달라졌다는 사용자 지적이다. OS title bar/파일 dialog와 정직한 미지원 상태는 구분하며 미구현 기능을 예시 성공으로 꾸미지 않는다. 진행은 [페이지별 교정 기록](../docs/ui-alignment.md)에 둔다.

- **2026-10-01 · UI-01** — 버튼의 크기·배치·강조를 행동의 중요도에 따라 구분한다. *이유:* 어떤 행동을 먼저 해야 하는지 시각적으로 드러내기 위해서다.
- **2026-10-01 · UI-02** — 현재 단계와 다음 행동을 설명 없이 이해할 수 있는 흐름을 만든다. *이유:* 처음 사용하는 사람도 마이그레이션 검사를 스스로 진행해야 한다.
- **2026-10-01 · UI-03** — 모든 작동 버튼에 해당 상태의 상호작용 피드백을 둔다. *이유:* 입력이 접수됐는지와 실행 가능 여부를 사용자가 알아야 한다.
- **2026-10-01 · UI-04** — 모든 버튼 실행에 기능과 연결된 애니메이션을 동반한다. *이유:* 실제 동작과 상태 변화를 인식시키며, 규칙을 적어도 자주 누락됐던 요구를 다음 화면 작업에서 반복 확인하기 위해서다.
- **2026-10-01 · 선택 요소의 완성도** — 기본 선택기의 외형에 기대지 않는다. DBMS 선택 카드, 스타일을 갖춘 체크박스·라디오, 검색·일괄 선택, 대응 대상의 선택·충돌 이유까지 설계한다. *이유:* 사용자 지적에 따라 선택 요소도 핵심 버튼과 같은 수준의 완성도를 갖춰야 한다. 운영체제 기본 조작 의미와 키보드 접근은 유지한다.
- **2026-10-01 · 데스크톱 전용** — 모바일 레이아웃과 좁은 모바일 폭의 검증을 제외한다. *이유:* 사용자가 C#·Avalonia의 Windows/macOS 데스크톱 앱이라고 범위를 재확인했다. 작은 데스크톱 창 조정과 모바일 화면을 혼동하지 않는다.

- **2026-10-01 · 헤더와 결과 행의 조작 영역** — 작게 분리한 펼침/세부 버튼 대신 헤더·결과 행 전체를 사용한다. 선택 체크박스는 별도 형제 입력이며 펼침과 선택이 서로 실행되지 않는다. 분류 헤더는 약 64 DIP, 입력 영역은 최소 44 DIP로 유지한다. 안내 아이콘·사전 확인 상태는 상하 중앙 정렬한다.
- **2026-10-01 · 준비 결과의 위치와 유효성** — 시험 준비 완료 정보는 버튼 우측에 표시하고 준비 전 경고를 완료 안내로 바꾼다. 준비 정보를 수정하면 완료 표시와 요약이 사라지고 재확인한다.
- **2026-10-01 · 숫자와 상세의 연결** — 정확한 판정 수치·공통 0 기준 축·분류 전체 행 상세를 함께 둔다. 결과 보기 동작에 짧은 애니메이션을 넣고 숫자를 가짜 중간값으로 세지 않는다. 첫 화면에는 결과 파일로 바로 보는 경로를 명시한다. 레퍼런스·상세 설계는 [제품 설계](../docs/product-design.md)에 둔다.

- **2026-10-01 · 시작 화면의 균형** — 새 검사·파일 열기·예시 보기를 한 행동 영역에 모으고 높이와 기준선을 맞춘다. 주요 진입 버튼의 채움·외곽선으로 우선순위를 유지하며 문구는 버튼 가운데 정렬한다. 파일 설명은 버튼 바로 아래에 둔다.

네 항목의 상세 정책·접근성 처리는 [RULE의 화면 설계 필수 기준](../RULE.md)이 정본이다. 화면 작업 시작 시 이 문서를 읽고, 버튼별 설계와 확인 증거를 [제품 설계](../docs/product-design.md)·[인수 기준](../docs/requirements.md)에 연결한다. 다른 프로젝트 전체에 적용되는 일반 기억으로 확대하지 않는다.
